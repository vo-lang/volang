## 方法与边界

- Apple M1 Pro，10 核，macOS Darwin 25.6.0，arm64；Node 24.16.0；Chromium 153.0.8010.12。
- Vue 与 Svelte 使用组件模板编译器的 production 模式；四个页面均由 esbuild 0.28.2 打包、压缩，目标 es2022。Vo 使用当前 CLI 的默认 Core Wasm 构建和字节码输出。
- 相同 1,000 行、语义 HTML/CSS、独立行计数、共享批量状态、keyed 换序及筛选；每次操作检查实际输出和保留节点身份。Vo 使用相同组件定义分别在 Wasm VM 与真实生成的 Core Wasm 中运行。
- 三轮轮换执行顺序，每个场景每轮预热 3 次、采样 20 次，共 60 个样本。耗时从原生事件派发开始，到输出匹配并强制布局结束，包含观察与检查成本，未测量实际屏幕绘制。
- 加载每个框架仅 3 次，以新浏览器 context 清空页面缓存；本机无压缩 HTTP，服务器 no-store，浏览器进程、操作系统和 Wasm 编译缓存可能已热。没有模拟移动设备、网络传输与线上访问。
- p99 只是当前小样本描述值。以下数据不可直接等同 INP/LCP，也不能外推所有应用。

模板编译方式依据 [Vue SFC 工具](https://vuejs.org/guide/scaling-up/tooling.html) 与 [Svelte compiler](https://svelte.dev/docs/svelte/svelte-compiler)，Svelte 挂载使用其 [命令式组件 API](https://svelte.dev/docs/svelte/imperative-component-api)。版本与依赖完整锁定在实验工作区。

## DOM、消息与内存观察

| 操作 | Vo 每次提交数 p50 | 消息字节 p50 | AOT 宿主处理 p50（ms） | VM 宿主处理 p50（ms） |
| --- | ---: | ---: | ---: | ---: |
| 单行计数 | 1 | 145 | 0.1 | 0.0 |
| 100 行批量计数 | 1 | 6,957 | 0.3 | 0.2 |
| 1,000 行换序 | 1 | 72,645 | 4.7 | 4.3 |
| 筛选 1,000 → 19 行 | 1 | 68,818 | 5.3 | 4.9 |
| 恢复 19 → 1,000 行 | 1 | 1,277,166 | 14.6 | 14.1 |

宿主计时包含批次解码、协议预检查和 DOM/平台应用，最终布局另由交互测试触发。单行只产生一个文本修改、批量计数只修改 100 处；结构变化仍重算大量 guest 组件。恢复列表产生 16,678 条协议操作和约 1.28 MB 消息。换序时 Vo 的组件范围带有注释锚点，浏览器观察到的 mutation record 数也高于参照；原始报告保留这些计数，不将 record 数等同真实工作量。

AOT 第一轮挂载的累计 guest 分配约 682 MB，全部更新后累计约 20.46 GB，guest 已提交内存从约 27.3 MB 上升至约 74.8 MB。这是累计分配与已提交容量，不能解释为同时存活了 20 GB。原始报告记录各轮 GC 次数、live bytes 与 JS/DOM 观察。VM 目前只暴露线性内存容量，本轮约从 44 MB 增至 63 MB，尚无等价的 Web VM collector 计数。

关闭页面 root 后实际内容均为空，再强制宿主 GC，DOM 节点数回落。测试仍保留运行时/统计控制对象，Wasm 内存也不会自动缩小；这组数据不能证明长期无泄漏，guest 与宿主指标不可相加当作同口径内存比较。

## Guest 分段诊断

独立 Node 诊断程序复用同一份 App/Row 定义，直接计时 `Root.Flush` 与 `json.Marshal`，通过两种 Wasm 后端各运行五轮更新。该镜像额外包含时钟/输出支持，运行环境也不同；下表用于分配优化优先级，与浏览器延迟单独报告。最终诊断单独执行，未与浏览器测试并发。

| 场景 | VM Flush / 编码 p50（ms） | AOT Flush / 编码 p50（ms） |
| --- | ---: | ---: |
| 1,000 行换序 | 61.1 / 31.6 | 218.6 / 177.1 |
| 筛选到 19 行 | 12.0 / 29.3 | 53.0 / 163.7 |
| 恢复 1,000 行 | 67.3 / 652.7 | 311.9 / 2777.3 |

恢复列表时通用 JSON 编码占 guest 阶段的主要部分；换序时组件渲染/比较也占显著比例。提交阶段通常小于 0.1 ms。因此优先从 schema 生成直接编码器，保留现有 JSON 线格式与兼容检查，先消除反射/临时对象成本；随后验证 props 稳定时的组件更新跳过与生命周期集合的延迟分配。

[分段诊断原始记录](../../target/ui-next/benchmark/baselines/20260913/phases/report.json)。

## 初始基线后的决策

1. 已通过分段计时定位 guest Flush 与编码成本，优先从 schema 生成直接编码器，减少通用编码开销；公开协议继续由单一 schema 管理，保留整批预检查和有界消息。
2. 降低换序时无关组件重算与短命集合分配；引入优化前明确 props/闭包/上下文失效规则，避免陈旧 UI。先保留普通 Vo 语义作为正确性参照。
3. 对生产运行入口实施能力裁剪：按需引入 Unicode、JSON、VFS 等支持；Web VM 的运行时/编译器分包另行验证。
4. 完成上述低复杂度改进后重跑相同样本；再依据剩余成本决定是否需要共享 Rust 内核或编译辅助直接更新。不会仅凭本基准就维护第二套组件语义。

下一轮工程目标先设为：本机单行和 100 行更新 p95 ≤ 16 ms，换序 p95 ≤ 50 ms，恢复列表 p95 ≤ 100 ms。它们是当前原型的改进目标，完整产品预算还需真实应用、移动端和加载测试校准，尚未接入 CI 性能门禁。
