**目标：让开发者用 Volang 自然地构建高质量 Web 界面，获得接近成熟框架的组件表达、交互可靠性、开发体验和交付能力。** UI 框架、组件库及开发工具是主体；Studio 是精简的展示和验证应用。交付顺序为 Web 优先，桌面随后跟进。Studio 的 Git、远程仓库管理和账户系统正式移除。

本版重新建立需求来源：用户目标 → 成熟框架的实际使用能力 → 典型开发任务与验收 → 公共 API → 实现架构。**现有 UI 作为 proof of concept，只参与迁移盘点、语言/后端约束识别和已知问题回归。** 旧目录、控件数量、协议划分和完成声明均不决定新框架的需求边界。

当前实现位于 `ui/next`；开发入口见[实现说明](../ui/next/README.md)，
逐项设计与历史证据见[实施记录](../ui/next/design.md)。当前开发 wire 为 v25，Web 完整交付检查点为 v25。
Vo 统一拥有组件、状态、派生、协调和生命周期；浏览器负责 DOM、原生输入与窄平台
适配。新的执行运行时和在线编译器已通过 `vo-ui-bridge` 移除旧 UI 内核依赖。
旧稳定 API 和默认兼容构建继续按[迁移清单](../ui/next/migration.md)过渡。

“接近主流水准”在本计划中指：下列首版任务可以通过公开 API 自然完成，常见错误能定位，实际交互可靠，性能有可复现的对照证据。庞大第三方生态、每个框架的全部高级特性不属于首版承诺。

## 4. 由需求推导架构，先验证影响全局的选择

### 已有依据的设计方向

1. **分清四层职责。** 核心管理组件/状态/生命周期；交互基础与 UIKit 管理可复用行为和设计系统；应用包提供路由/数据/表单/SSR；工具提供创建/开发/检查/测试/构建。依赖可裁剪，简单组件使用不承担完整应用框架成本。
2. **Web 使用语义 HTML 和浏览器 CSS。** 类型化常用 API 与明确的平台扩展并存。桌面适配随后设计，共享组件行为和状态规则，按能力说明差异。
3. **各后端执行同一套组件契约。** 编译器、运行时、浏览器桥接的职责集中定义，状态、事件、生命周期和错误处理避免分叉。语言核心继续独立于 UI；renderer-neutral Rust 包保持向内依赖及已声明的 no_std 边界。
4. **将浏览器即时行为纳入正式模型。** 默认动作、输入法、选择和焦点需要在适当时机由宿主处理；Wasm 异步往返必须有输入同步契约。框架业务状态与原生输入的临时状态各有明确归属。
5. **默认实现追求少做工作。** 保留实例与 DOM，批量跨宿主提交，更新局部依赖；动态结构用有界 keyed 处理。状态与任务随作用域清理，队列使用通知推进。优化机制服务于真实用例。
6. **共享行为与外观分层。** UIKit 可以直接使用，也能用公开组合点替换外观。基础行为需经多个控件实际复用后再抽象，避免先建设复杂插件系统。

### P0/P1 要作出的具体选择

| 选择 | 候选方向 | 决策依据 |
| --- | --- | --- |
| 状态 API | 显式类型化状态单元/更新函数；必要的编译辅助语法 | T1/T2 的表达、跨函数/跨包行为、结构化数据可预测性、诊断能力；不为语法简短制造隐式漏更新 |
| 更新粒度 | 组件级局部更新；编译辅助的 binding/依赖更新 | T1/T4 的更新量、内存、调试和实现复杂度；静态与动态结构共享身份/生命周期 |
| 组件运行时位置 | Volang 库主导，或共享 Rust 内核加必要的 guest 接口 | Wasm VM/Core AOT 的调用开销、对象所有权、GC、包体、调试及后续桌面接入；单一语义来源优先 |
| 内容与样式表达 | 普通 Vo 组合 API，配合带类型的内容函数、样式接口和 CSS 资源 | 能表达嵌套内容、动态列表和组件包装；错误定位准确；真实语言工具链能处理 |
| Web 扩展边界 | 框架/扩展包拥有桥接，应用消费类型化 Vo 接口 | T6 能接入现成控件；挂载/更新/清理明确；平台专用包与可移植组件分开 |
| SSR 与接管 | 服务端 HTML、稳定身份和可序列化初始数据；客户端复用节点 | T5 的提前输入、请求隔离、动态分支、错误恢复与加载成本 |

上一版建议的“组件运行时全部用 Volang 编写”降为候选方案。需求阶段不预先锁定内存布局、消息格式、crate 数量或所有更新都编译为直接写 DOM。用少量纵向原型选定一套方案，随后删除落选原型，避免同时维护多套内核。

现有架构文档中的“无浏览器专用组件 API”“宿主适配不作为扩展面”等约束，需要结合 R12/R15 明确修订边界：保留应用以 Vo 编写的体验，允许受管理的平台扩展包。此处属于重写提案，现行稳定契约与声明尚未改变。

## 5. 如何衡量达到主流水准

### 正确性和可用性

- R01–R30 分配所有者、阶段、可执行用例和文档示例；标记区分设计、实现、执行验证、真实应用使用及稳定交付。
- T1–T6 使用真实 Vo 编译产物。Web 分别执行 Wasm VM 与 Core Wasm AOT；后续桌面分别运行 VM/JIT/链接后的 Native AOT 程序。
- 保留不等待 render-idle 的连续输入、组合输入、立即提交、列表换序、请求乱序、取消、卸载和热更新交错用例。内部 readiness 信号不能替代这些测试。
- Chrome/Edge、Firefox、Safari 覆盖各自浏览器引擎；触摸、移动视口和输入法需要相应平台验证。自动化语义检查补充人工键盘和读屏验收，不能声称自动测试覆盖全部辅助技术行为。
- 组件单独通过后，继续验证组合场景：Dialog 内表单/Combobox、虚拟列表内选择、导航中的异步任务、自定义 Trigger 与主题覆盖。
- 框架处理的可恢复错误验证局部恢复；运行环境中断验证 root 重建和草稿恢复。不能承诺回滚已经发生的外部副作用。

### 性能、资源和复杂度

成熟框架的性能评估区分首次加载与后续更新，参考 [Vue 性能指南][vue-performance]。Web Vitals 给出的良好体验门槛为 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1，并按真实访问的第 75 百分位评估；实验室结果与线上数据分别报告。[Web Vitals][web-vitals]

这些指标作为产品体验参考，达标本身不能证明与某框架性能相当。Wasm 的异步状态更新还要测量“用户操作到业务结果实际可见”的端到端延迟，避免短事件处理回调掩盖后续长时间等待。

| 测量域 | 必须报告的内容 |
| --- | --- |
| 加载 | 冷/热缓存；有用 HTML、首个可交互控件、Wasm 编译与接管完成；初次进入编辑器/编译器单列 |
| 交互 | 输入、校验、打开弹层、筛选、路由切换的 p50/p95/p99；包含调度、桥接、布局与最终呈现 |
| 更新规模 | 1,000 行局部修改/换序；100,000 条虚拟数据；记录受影响组件、DOM 修改和宿主调用数 |
| 内存 | guest GC 与宿主 JS/DOM 两侧；峰值和稳定占用；重复导航/卸载后任务、监听和资源回落 |
| 产物 | 首屏和后续下载；压缩/未压缩体积；应用 Wasm、宿主 JS、运行时、样式、字体/图片分别列出 |
| 开发速度 | 创建到预览、冷构建、增量更新、报错及修复恢复；典型编辑是否保留局部状态 |

P0 固定测试机、浏览器、框架版本、数据、生产构建选项和网络/缓存条件；对照页面保持相同功能与可访问要求。P1 用实测制定各场景的绝对预算和相对容差，写入可复现基准及 CI；预算未明确前不将性能标为验收通过。旧 PoC 的数字仅作为历史记录。

先处理成数量级增长的工作、重复计算/复制、全量提交和无效轮询。引入专用优化前写出实测收益及维护成本；达到已确定的体验预算后停止该项优化。首版不以某个微基准排名驱动框架架构。

## 6. Studio 与全部第一方使用者

Studio 固定三个主要入口：**Gallery、Playground、Docs**。

- Gallery：交互状态、主题切换、可复制代码及少量完整页面；组件实际消费新公共 API。
- Playground：选择示例 → 编辑 → 运行/预览；提供错误定位、输出、停止、重置和本地草稿恢复。输入法、选择、粘贴、撤销、基础着色及滚动优先。
- Docs：导航、搜索、目录、深链接、可运行示例；正文先展示，在线编译器进入 Playground 后按需加载。
- 三者保持一致的排版、颜色、间距、图标、加载/空/错误状态，完整支持暗色、窄屏和键盘操作。

Studio 是框架的消费者。框架的组件能力、路由或数据 API 不围绕编辑器工作区设计；T1–T6 中的独立用例用于防止框架只能服务 Studio。

新 Studio 正式移除 Git、远程仓库管理和账户功能。对应页面、宿主操作、协议、测试和产品声明随重写删除；用户已有项目文件、Git 数据和草稿保留恢复/导出通道。复杂项目中心、多窗口工作区和完整 IDE 能力退出首版。

Studio 的第一方 shell、catalog、playground、editor 接入、preview、docs、persistence 全部重写。编辑器内核可通过受管理的适配复用成熟依赖；是否采用根据输入质量、体积和接入成本验证。专业编辑器从零实现不作为 UI 成熟度门槛。

其余 `ui/` 库、UI 编译/执行适配、Web/桌面宿主、示例、模板、展示应用、测试工具、文档生成接入及交付流程纳入重写盘点。保留的消费者全部接入新体系；重叠或低价值应用合并/移除。现有语言编译器、执行后端、模块系统及第三方平台库作为接入平台，UI 专属耦合由新实现替换。

## 附录 A：PoC 的用途与迁移盘点

旧代码只回答以下问题：有哪些使用者需要迁移；语言和后端有哪些真实接入限制；哪些数据要保留；哪些失败场景应进入回归。旧产品清单逐项记录“重写、合并、移除、后续”，并关联新需求编号；未出现在旧清单的成熟框架需求仍按 R01–R30 交付。

下面保留先前代码审查证据，用于迁移和回归输入。表中的改进方向属于候选设计，最终以第 3–5 节的需求和验证结果为准。


| 问题 | 已查到的证据 | 新设计的要求 |
| --- | --- | --- |
| 多套 UI 执行语义 | VM 的 `MountedRuntime` 同时包含 Generic、Template、Component；Core Wasm 的 JS 宿主独立管理状态、组件作用域和树比较 | 组件状态、调度和生命周期只有一个语义实现；后端仅负责调用和调度接入 |
| 编译计划没有贯通真实应用 | 静态组件限制包含 single-return/prelude；复杂组合走 fallback；Core 宿主 `begin` 返回通用渲染路径 | 普通条件、列表和跨包组件直接属于正式模型；局部动态分支与静态更新使用同一实例模型 |
| 生命周期分层断开 | 编译器生成的 definition 中 effects/tasks 为空；Vo 任务库另设全局 registry，通过 25 ms 扫描清理、1 ms 等待提交和流队列空间 | 运行时显式发布提交、取消和队列可写通知；任务归属于组件作用域 |
| 身份与渲染版本耦合 | `ui.Mount` 每轮清空 handler 表；Core 宿主把当前 revision 作为 handler generation；DOM 丢弃不匹配事件 | 实例生命周期、handler 身份和提交版本分离；连续输入不会仅因无关提交而失效 |
| 更新工作容易扩大 | Core 宿主每轮建立视图对象、Map、副本，遍历完整树；keyed 匹配对每个节点调用旧子列表 `find` | 保留组件实例和节点；显式 dirty 集；局部重建；keyed 匹配有线性索引和边界 |
| 全局环境与作用域较脆弱 | Vo 中存在 environmentStack/runtimeHandlers；任务 registry 也由包级变量承载 | 每个 UI root/session 明确拥有环境、handler、任务与清理，跨窗口共享对象显式传入 |
| Studio 是集中状态应用 | `app.vo` 4,969 行，`State` 105 个字段，混合锁、取消代次、业务操作和视图 | 按业务拆模块；UI 状态由一个明确的写入者推进，后台返回类型化结果 |
| 编辑投影和编辑成本不一致 | Document 每次 `applyRaw` 分配并复制完整 rune 数组；可见行虚拟化只减少显示工作 | 增量文本存储、行索引和修改记录；输入接口传编辑操作；大文件编辑本身也要测试 |
| 协议与宿主容易分叉 | UI Rust/TS 编解码、属性编号和限额分别维护；Studio Vo 接口、JS/Rust operation 分发手工对应 | 一个协议定义生成类型、编号、编解码与一致性测试；保留真实平台适配实现 |
| 工具代码承载过多职责 | UI compiler 3,923 行、VM adapter 5,603 行、UI CLI 5,669 行，单文件跨多类职责 | 按生命周期、编译、宿主服务、构建与测试边界组织代码，避免继续叠加分支 |
| 局部证据容易被解释成整体能力 | 部分 `...aot_equivalent` 测试只比较 VM/JIT 初始树并检查 AOT 产物非空；微基准使用自建 plan 和简化 renderer | 编译、执行、平台交互、性能证据分别记录；真实 `.vo` 应用必须走新生产路径 |
